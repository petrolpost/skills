# 规则体系分类参考手册

本文件为 `pattern-hunter` skill 的分析参考，定义体系识别的详细分类和信号词。

---

## 分层体系总览

规则系统的识别遵循**三层递进**结构：

```
业务体系（业务域 + 设计范式）
  └── Agent 规则体系
        ├── 治理输出（对外提供的规则体系）
        ├── 治理输入（项目自身遵守的规则体系）
        └── 自引用状态（强/弱/无）
              └── 子体系（功能/结构/治理）
```

- **第一层（业务体系）**：识别 Agent 服务的业务域 + 设计范式
- **第二层（Agent 规则体系）**：区分治理输出和治理输入，检测自引用
- **第三层（子体系）**：在确定的 Agent 规则体系下，拆解为功能/结构/治理子体系

---

## 第一层：业务体系（Business System）

### 1.1 业务域识别

业务体系是规则系统服务的**业务领域**，定义了 Agent 的核心价值和适用范围。

#### 识别方法

回答三个问题：
1. **业务场景**是什么？（客服、代码审查、数据分析、内容创作...）
2. **服务对象**是谁？（终端用户、开发者、运营人员...）
3. **业务目标**是什么？（提升效率、保证质量、降低风险...）

#### 常见业务体系类型

| 业务体系 | 典型规则特征 | 信号词 |
|----------|-------------|--------|
| 客服/售后体系 | 工单处理、退换货、投诉、满意度 | customer, ticket, order, refund, satisfaction |
| 代码审查体系 | PR 评审、lint 检查、安全扫描 | PR, review, lint, vulnerability, security |
| 数据分析体系 | 报表生成、指标监控、异常检测 | report, metric, dashboard, anomaly |
| 内容创作体系 | 文章生成、风格控制、SEO 优化 | article, blog, SEO, tone, keyword |
| 项目管理体系 | 任务分配、进度跟踪、风险管理 | task, milestone, risk, timeline |
| 通用助手体系 | 多领域能力，无明显业务聚焦 | general, assistant, multi-domain |
| 治理/框架体系 | 定义规则 Schema、验证机制、适配层 | schema, governance, adapter, validator, rule system |

#### 置信度量化

| 证据类型 | 加分 | 说明 |
|----------|------|------|
| 显式声明业务域 | +30% | 规则中直接说明"我们服务于 XX 业务" |
| 术语一致性 | +10%/处 | 全文使用统一的领域术语 |
| 多文件印证 | +10%/文件 | philosophy、spec、examples 都指向同一业务域 |
| 行为证据 | +10% | 规则的实际行为符合业务场景 |
| 反面证据 | -20%/处 | 存在与声明矛盾的业务规则 |
| 基准 | 50% | 无任何证据时的默认值 |

### 1.2 设计范式识别（新增）

设计范式是规则系统的**哲学定位**，通常比业务场景更抽象。它解释了"为什么这样设计"。

#### 识别方法

1. **范式声明扫描**：规则中是否有明确的范式声明？（如"Governance ≠ Control"、"Autonomy First"）
2. **对比/转变检测**：是否有从旧范式到新范式的转变描述？
3. **NOT 声明提取**：规则中明确说"不是什么"的部分
4. **术语演变追踪**：旧术语被新术语替代的原因说明

#### 常见范式类型

| 范式类型 | 特征 | 信号词 |
|----------|------|--------|
| 治理≠控制 | 声明边界而非流程 | Governance ≠ Control, Declarative not imperative |
| 自治优先 | Agent 自主性高于约束 | Agent Autonomy First, Runtime knows best |
| 声明优于实现 | 描述 What 而非 How | Declarative, Schema not framework |
| 运行时不可知 | 不与特定 Runtime 绑定 | Runtime Agnostic, Platform Independent |
| 能力抽象 | 能力声明独立于实现 | Capability > Skill, Abstract not concrete |
| 范式转变 | 从旧模型升级到新模型 | X → Y, Evolution from..., Replaced... by... |

#### 范式转变检测

当检测到范式转变时，记录：
- **旧范式名称**：如 PCS (Persona-CheckPoint-Skill)
- **新范式名称**：如 PGC (Persona-Governance-Capability)
- **转变原因**：如"CheckPoint 暗示流程控制，违背治理理念"
- **术语替换表**：如 CheckPoint→Governance Gate, Skill→Capability
- **影响范围**：哪些文件/规则受到了转变的影响

## 第二层：Agent 规则体系（Agent Rule System）

### 2.1 治理输出（Governance Output）

项目对外提供的规则体系/Schema/框架，用于治理其他 Agent。

#### 识别要点

1. **对外接口**：是否有 YAML Schema、Adapter、配置文件格式？
2. **使用示例**：examples/ 目录、demo 场景、最佳实践？
3. **验证机制**：validator、测试、CI 检查？
4. **文档链**：philosophy → spec → runtime-mapping → contributing？

#### 输出格式

- 体系名称
- 对外接口清单（Schema 文件、Adapter 列表）
- 验证机制（validator、测试覆盖）
- 使用示例数量

### 2.2 治理输入（Governance Input）

项目自身遵守的规则体系，描述项目内部如何运作。

#### 识别要点

1. **开发工作流**：Issue-Driven、分支规范、Commit 规范？
2. **架构红线**：禁止项、依赖限制、术语约束？
3. **知识引用链**：philosophy → spec → runtime → contributing？
4. **加载策略**：always-on vs on-demand？

#### 输出格式

- 体系名称
- 工作流阶段（如 Issue-Driven 的四阶段）
- 架构红线清单
- 知识引用链

### 2.3 自引用检测（新增）

检查"治理输出"和"治理输入"是否存在**自引用关系**。

#### 自引用强度评估

| 强度 | 条件 | 示例 |
|------|------|------|
| 强自引用 | 治理输入的工作流/验证方式与治理输出的机制一致 | PGC 用 PGC Schema 验证自己的 PR |
| 弱自引用 | 部分概念复用，但机制不完全一致 | 使用了 Persona 概念但没有 Gate 验证 |
| 无反向引用 | 治理输出和治理输入完全独立 | 两个体系没有交集 |

#### 自引用分析输出

- 自引用强度：[强/弱/无]
- 复用概念：[哪些概念被双向使用]
- 一致性检查：[治理输入是否违反了治理输出的规则]
- 成熟度评价：[自引用是理念的验证还是遗漏]

## 第三层：子体系（Sub-Systems）

在确定业务体系和 Agent 规则体系后，向下拆解为具体子体系。

### 子体系识别的起点：文件引用关系图

**引用体系**是子体系识别的起点。绘制文件间的引用关系：
- 追踪 `@import`、`see also`、`reference`、`详见`、`参见`、`before referencing` 等引用指令
- 标出循环引用风险
- 引用关系帮助识别：
  - 知识的层次结构（philosophy → spec → runtime-mapping）
  - 规则的加载策略（always-on → on-demand）
  - 模块间的依赖边界

### 功能子体系（Functional Sub-Systems）

#### 记忆体系 (Memory System)
Agent 如何存储、检索、更新、遗忘信息。

**信号词：**
`remember`, `store`, `recall`, `forget`, `context window`, `session`, `persist`,
`记住`, `存储`, `上下文`, `遗忘`, `历史`

**典型规则形态：**
- "在对话开始时加载用户偏好"
- "超过 N 轮后压缩历史"
- "重要决策必须写入 memory.md"

**健康度检查：**
- [ ] 存储触发条件明确？
- [ ] 检索时机定义了吗？
- [ ] 有没有遗忘/更新策略？
- [ ] 跨会话行为定义了吗？

---

#### 工具体系 (Tool System)
工具的声明、调用规则、结果处理、失败处理。

**信号词：**
`tool:`, `use <tool>`, `call`, `invoke`, `available tools`, `when to use`,
`工具`, `调用`, `执行`, `失败`, `重试`

**典型规则形态：**
- "只在用户明确要求时使用搜索工具"
- "工具调用失败后最多重试 2 次"
- "优先使用内置工具，外部 API 作为备选"

**健康度检查：**
- [ ] 工具列表是否完整？
- [ ] 调用前置条件定义了吗？
- [ ] 失败处理有没有？
- [ ] 并发调用规则有吗？

---

#### 工具路由体系（新增）
当存在多个候选工具/数据源时，决定**该用哪一个**的优先级机制。**与工具体系的区别**：工具体系管"单个工具怎么调用"，工具路由体系管"多个工具谁该被选中"。

**信号词：**
`prefer`, `prioritize`, `instead of`, `before falling back to`, `route to`,
`优先使用`, `而非`, `先于`, `路由`, `备选`

**典型规则形态：**
- "公司内部数据查询优先用内部工具，而非通用网页搜索"
- "命名了具体服务时跳过推荐流程，直接调用"
- "多个工具都能满足需求时，按工具列表声明顺序选择"

**健康度检查：**
- [ ] 多个工具同时满足触发条件时，优先级顺序是否明确？
- [ ] 是否区分了"用户明确指定工具"和"系统自动选择工具"两种场景？
- [ ] 路由失败（首选工具不可用）时的降级路径是否定义？

---

#### 角色体系 (Persona System)
Agent 的身份、语气、人格、角色切换逻辑。

**信号词：**
`you are`, `as a`, `persona`, `role`, `tone`, `style`, `voice`,
`你是`, `身份`, `角色`, `语气`, `人格`

**典型规则形态：**
- "你是一个专业的技术顾问，不使用过于口语化的表达"
- "当用户情绪激动时切换到更柔和的语气"

**健康度检查：**
- [ ] 身份定义是否一致（多处无冲突）？
- [ ] 是否有角色切换的明确触发条件？
- [ ] 语气规则是否可测试？

---

#### 输出体系 (Output System)
输出格式、长度、语言、结构规则。

**信号词：**
`format`, `length`, `markdown`, `json`, `respond in`, `always output`,
`格式`, `长度`, `输出`, `语言`, `结构`

**典型规则形态：**
- "代码块必须标注语言类型"
- "回复不超过 500 字除非用户要求详细"
- "列表超过 3 项才使用 bullet points"

---

### 结构子体系（Structural Sub-Systems）

#### 触发体系 (Trigger System)
哪些输入信号激活哪些行为。

**信号词：**
`when`, `if`, `trigger`, `on`, `detect`, `recognize`,
`当`, `如果`, `触发`, `识别`, `检测`

**典型规则形态：**
- "当用户提到价格时，调用定价工具"
- "识别到代码请求时，切换到技术专家模式"

**健康度检查：**
- [ ] 触发条件是否互斥？（多个触发同时满足时怎么办）
- [ ] 是否有 default/fallback 触发？

---

#### 流程体系 (Process System)
步骤编排、工作流、状态机。

**信号词：**
`step`, `first`, `then`, `after`, `before`, `workflow`, `phase`, `stage`,
`步骤`, `流程`, `阶段`, `先`, `然后`, `之后`

**典型规则形态：**
- "收到需求后：1. 澄清 2. 方案 3. 实现 4. 验证"
- "必须在输出结论前先展示推理过程"

---

#### 引用体系 (Reference System)
文件间依赖关系、@import、外部知识引用。

**信号词：**
`@import`, `see`, `refer to`, `load`, `include`, `source`,
`参见`, `引用`, `加载`, `包含`, `before referencing`, `knowledge base`

**输出重点：**
- 绘制文件依赖图
- 标出循环引用风险
- 识别知识的层次结构（philosophy → spec → implementation）
- 识别加载策略（always-on → on-demand）

---

### 治理子体系（Governance Sub-Systems）

#### 权限体系 (Permission System)
允许/禁止的行为边界。

**信号词：**
`never`, `must not`, `forbidden`, `only`, `restricted`, `allowed`,
`禁止`, `不得`, `只能`, `允许`, `限制`

**健康度检查：**
- [ ] 禁止规则是否有优先级？
- [ ] 是否有灰色地带未覆盖？
- [ ] 是否有规则相互矛盾？（重点检查）

---

#### 优先级体系 (Priority System)
规则冲突时的解决机制。

**信号词：**
`priority`, `override`, `fallback`, `default`, `unless`, `except`,
`优先`, `覆盖`, `默认`, `除非`, `例外`

**典型规则形态：**
- "安全规则优先于用户偏好"
- "明确指令覆盖系统默认"

---

#### 安全体系 (Safety System)
拒绝策略、越狱防护、敏感内容处理。**性质：防御性**——针对恶意/越界输入做拒绝判断。

**信号词：**
`refuse`, `reject`, `harmful`, `safe`, `jailbreak`, `ignore previous`,
`拒绝`, `有害`, `安全`, `敏感`, `越狱`

---

#### 内容合规体系（新增）
版权、引用规范、知识产权、争议性内容的中立性处理。**性质：边界性**——不是"拒绝整个请求"，而是"在请求内部限定输出形态"。

**信号词：**
`copyright`, `quote`, `citation`, `fair use`, `attribution`, `paraphrase`, `IP`,
`引用`, `版权`, `字数限制`, `转述`, `知识产权`, `中立`

**典型规则形态：**
- "每次引用不超过 N 词，单一来源最多引用一次"
- "政治/争议性话题保持中立，呈现多方观点而非单一立场"
- "禁止逐字复现歌词/诗歌"

**与安全体系的区别：** 安全体系问的是"要不要做这件事"，内容合规体系问的是"做的时候边界在哪"。两者常被信号词混淆（都含"禁止"类词），但触发条件和处理方式完全不同——前者整体拒绝，后者部分改写/限定。

**健康度检查：**
- [ ] 引用/转述的量化边界是否明确（词数、次数）？
- [ ] 是否区分了"完全拒绝"和"部分限定"两种处理路径？
- [ ] 争议性话题的中立性要求是否有具体执行机制（而非只是原则声明）？

---

#### 用户福祉体系（新增）
对用户心理/情绪/健康状态的前瞻性关怀机制。**性质：关怀性**——主动识别风险信号并提供支持，而非被动拒绝有害请求。

**信号词：**
`well-being`, `crisis`, `self-harm`, `mental health`, `distress`, `validate`,
`福祉`, `心理健康`, `危机`, `情绪`, `自我伤害`, `求助资源`

**典型规则形态：**
- "识别到自杀风险信号时主动提供危机资源，不等待用户明确求助"
- "避免对用户的情绪做诊断性归因，只描述观察到的内容"
- "讨论敏感健康话题时，区分'提供事实信息'和'给出医疗建议'两种角色"

**与安全体系的区别：** 安全体系的默认动作是"拒绝/拦截"，用户福祉体系的默认动作是"识别风险后仍然帮助，但调整帮助的形式"（如提供资源而非满足危险请求本身）。如果把这类规则归入安全体系，会丢失"主动关怀"和"被动拒绝"这个关键的行为差异。

**健康度检查：**
- [ ] 风险识别后的动作是"提供资源"还是简单"拒绝"？两者性质不同需分别检查
- [ ] 是否有"避免诊断性归因"的边界（防止 Agent 过度推断用户心理状态）？
- [ ] 危机场景下是否明确"不能做什么"（如不能要求用户先澄清才给资源）？

---

#### 术语治理体系（新增）
术语的一致性管理和禁用/批准机制。

**信号词：**
`approved terms`, `prohibited terms`, `use instead of`, `terminology`, `mandatory`,
`批准术语`, `禁用术语`, `必须使用`, `禁止使用`, `术语一致性`

**典型规则形态：**
- "严禁使用 CheckPoint，必须使用 Governance Gate"
- "术语一致性是架构红线之一"

**健康度检查：**
- [ ] 是否有明确的批准/禁用术语表？
- [ ] 术语约束是否在所有文件中强制执行？
- [ ] 术语演变是否有文档记录？

---

#### 架构边界体系（新增）
模块依赖限制、NON-GOALS 声明、架构红线。

**信号词：**
`architecture boundaries`, `non-goals`, `zero runtime deps`, `never reverse-depends`,
`架构边界`, `非目标`, `零依赖`, `严禁`, `红线`, `禁止反向依赖`

**典型规则形态：**
- "pgc_core 零运行时依赖"
- "pgc_adapter 从不反向依赖 pgc_core"
- "NON-GOALS: 不提供工作流引擎"

## 隐式体系识别（高级）

有些体系没有明显信号词，需要语义推断：

| 隐式体系 | 识别方法 |
|----------|----------|
| 隐含业务体系 | 规则中反复出现特定领域的术语和场景，但没有明确声明 |
| 隐含角色体系 | 规则中反复出现"你应该/不应该"，但没有明确角色声明 |
| 隐含优先级体系 | 多条规则覆盖同一场景，但没有冲突解决机制 |
| 隐含状态机 | 有"之后/完成后/下一步"逻辑但没有明确状态定义 |
| 隐含记忆体系 | 规则要求跨轮次一致性但没有存储机制 |
| 隐含失败处理 | 规则详细描述正常路径，但工具失败/输入异常/资源不可用时该怎么办完全没提 |
| 隐含范围边界 | 规则定义了"做什么"，但没定义"何时算完成/何时该停止/何时升级给人工" |
| 隐含自引用 | 治理输入遵守了治理输出的规则，但没有明确声明 |
| 隐含范式转变 | 新旧术语并存，但没有明确的转变说明 |

当识别到隐式体系时，在体系地图中标注 ❓（隐式存在，未正式定义），并在分析中建议是否需要正式化。
