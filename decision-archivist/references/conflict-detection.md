# 冲突检测规则

## 1. 检测触发时机

仅在全量梳理阶段的 Step 4 执行,不在自动感知阶段做冲突检测(信息量不足,判断不可靠)。

## 2. 检测流程

对每一条**新写入**的决策记录 D_new,与 `decisions.yaml` 中**所有已有**决策记录做以下比对:

1. **元素重叠检查**:D_new.related_elements 与 D_old.related_elements 是否存在交集(同一 `type` + `ref`)
2. 若无交集 → 跳过,检查下一条
3. 若有交集 → 进入语义比对

## 3. 语义比对:是延伸还是矛盾

对存在元素重叠的一对决策 (D_old, D_new),判断两者关系:

### 关系 A:显式延续(不算冲突)

D_new 已经通过以下任一方式明确声明与 D_old 的关系:
- `D_new.supersedes == D_old.id`
- `D_new.rationale` 中明确提及"取代/基于/延续 D_old 描述的方案"

→ 标记为正常演进关系,在渲染时用"取代"箭头连接,不进入冲突列表。

### 关系 B:自然延伸(不算冲突)

D_old 和 D_new 的 `change.to` 描述的方案在逻辑上**兼容**(D_new 是在 D_old 基础上的细化,而不是否定):

例如 D_old："引入缓存层" ,D_new："缓存层选用 Redis 而非 Memcached" —— 这是细化,不是矛盾。

→ 不进入冲突列表,可选择性在 related_elements 中互相标注关联。

### 关系 C:潜在冲突(需要标记)

D_old 和 D_new 在**同一关联元素**上给出了**互斥的结论**,且:
- 没有 `supersedes` 关系声明
- 时间上 D_new 并未明确说明是在否定 D_old

例如:
- D_old(6月15日,关联 `auth-module`):"必须无状态,不允许服务端存会话"
- D_new(7月1日,关联 `auth-module`):"引入会话缓存以支持长连接"

两者在同一模块上的结论互斥,且没有任何一条声明"这取代了之前的方案" → 标记为 ⚠️ 潜在冲突。

## 4. 冲突判断的保守原则

- **宁可多报,不可漏报。** 冲突检测的目的是把疑点交给用户判断,不是自己下结论替用户排除。拿不准是否互斥时,倾向于标记为潜在冲突。
- **不要自动"解决"冲突。** 即使能猜到大概率是后者取代了前者,也不要擅自把 D_old 标记为 `superseded`——这个判断权在用户,skill 只负责暴露问题。
- **跨会话冲突同样要检测。** 冲突不限于同一次对话内的前后矛盾,不同批次的全量梳理写入的决策之间同样要做比对,这也是为什么每次全量梳理都要读取完整的 `decisions.yaml`,而不能只看本次新增内容。

## 5. 输出

冲突以列表形式汇总在 `DECISION_LOG.md` 末尾的"⚠️ 潜在冲突"章节,同时在向用户汇报的摘要中列出,格式见 `record-schema.md` 第 3 节。
