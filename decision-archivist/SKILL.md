# decision-archivist

追踪 Agent 设计过程中思想/逻辑/方案的变更决策,防止版本间逻辑断层与方案冲突。

## 核心理念:标记与精读分离

决策记录不是"边聊边问清楚",而是**两阶段**的:

```
对话进行时 → 轻量标记(不打断)  →  .petrolpost/agent-decisions/staged-signals.yaml
                                            │
用户要求梳理时 → 全量精读+补全  →  .petrolpost/agent-decisions/decisions.yaml
                                            │
                                    渲染  →  DECISION_LOG.md
```

- **自动感知**只负责"占位":发现疑似变更就记一笔时间戳+触发语句+粗略新旧方案,信息不全也先记下,绝不打断对话去追问。
- **全量梳理**才是真正提取四要素(触发因素/变更理由/关联元素/计划后续措施)的地方,此时会系统回读上下文,并优先处理 staged-signals 里积压的标记。
- 两者共享同一套存储结构,全量梳理会把已处理的标记从 staged 移入正式记录。

**不要在自动感知阶段编造理由。** 如果当时的发言里没有说明"为什么改",就把 `rationale` 字段留空并标注 `待补全: true`,交给全量梳理阶段向用户确认,而不是替用户猜一个理由写死。

## 存储结构

所有输出统一写入项目根目录下的 `.petrolpost/agent-decisions/`:

```
.petrolpost/agent-decisions/
├── config.yaml            # 开关配置(如自动感知是否开启),缺省时按默认值创建
├── decisions.yaml        # 源真值:已确认/待补全的正式决策记录(结构化)
├── staged-signals.yaml   # 自动感知产生的轻量标记,尚未纳入正式记录
└── DECISION_LOG.md        # 由 decisions.yaml 渲染出的可读时间线(不要手工编辑此文件)
```

首次使用时,若该目录不存在,先创建四个文件的初始骨架(`config.yaml` 按默认配置生成,其余为空列表 + 说明性表头),再继续。

字段定义、ID 规则、YAML 示例见 `references/record-schema.md`。**写入 decisions.yaml 前务必核对该文件里的字段名和格式,不要自创字段。**

## Step 0: 读取配置(每次被触发时都先做)

读取 `.petrolpost/agent-decisions/config.yaml`:

```yaml
auto_sense_enabled: true   # 是否开启"模式一:自动感知"。默认为 true。
```

- 若文件不存在 → 创建该文件,写入默认值 `auto_sense_enabled: true`
- 若 `auto_sense_enabled: false` → 本次会话中**跳过模式一**的全部行为(不检测信号词、不写 staged-signals.yaml),只在用户明确要求全量梳理时执行模式二
- 若 `auto_sense_enabled: true` → 正常执行模式一 + 模式二

### 开关的调整方式

用户可以随时用自然语言调整开关,不需要特殊指令格式,例如:

- "关闭自动感知" / "先别自动记录了" / "turn off auto-sense" → 将 `auto_sense_enabled` 改为 `false`,写回 `config.yaml`,并简短确认("好,已关闭自动感知,之后只在你要求梳理时才处理")
- "打开自动感知" / "恢复自动记录" / "turn on auto-sense" → 改为 `true`,同样简短确认

调整开关本身**不需要**追问原因,直接执行并确认即可,这属于用户对本 skill 行为方式的直接配置,不是需要澄清的模糊请求。

### 开关只影响模式一,不影响模式二

无论 `auto_sense_enabled` 是 true 还是 false,用户明确要求"帮我梳理决策历史"时,模式二(全量梳理)照常执行——开关关闭只是意味着这次梳理没有 staged-signals 可以作为线索起点,全量梳理会更依赖独立的全文扫描(见 Step 2)。

## 模式一:自动感知(默认开启,轻量、静默;可通过 config.yaml 关闭)

### 何时触发

`auto_sense_enabled` 为 true 时,当前设计讨论中,某句发言里出现变更信号词,且是针对**思想/逻辑/方案**层面的变更(不是措辞/格式调整)。信号词清单和"是否算实质性变更"的判断标准见 `references/signal-taxonomy.md`。

### 该做什么

在 `staged-signals.yaml` 追加一条轻量记录:

```yaml
- signal_id: SIG-20260703-01
  detected_at: "2026-07-03T10:20:00"
  trigger_utterance: "原文摘录,不超过一两句,足够回溯上下文即可"
  rough_from: "旧方案的粗略描述(能识别就填,不能识别留空)"
  rough_to: "新方案的粗略描述"
  rationale: null
  待补全: true
```

### 该做什么(禁止项)

- 不追问"为什么改这个"
- 不打断当前讨论节奏,不主动汇报"我记录了一条变更"
- 不为了填满字段而编造理由或关联元素
- 不在自动感知阶段写入 `decisions.yaml` 正式记录——正式记录只在全量梳理阶段产生

### 例外:用户主动说明理由时

如果用户在同一段发言里**已经**给出了理由(例如"改用方案B,因为方案A性能不够"),照实摘录进 `rationale`,不必等到全量梳理再补。这不算"打断追问",只是顺手记录已有信息。

## 模式二:全量梳理(主流程,手动触发)

用户明确要求时执行。这是本 skill 的核心工作流程。

### Step 1: 确认材料范围

判断本次梳理的输入来源,向用户简要确认(不必用交互式提问工具,一句话确认即可):

| 来源 | 处理方式 |
|---|---|
| 当前对话全文 | 直接作为分析对象 |
| 用户指定的历史对话/文档路径 | 用 `view` 读取 |
| 已有的 `staged-signals.yaml` | 必读,作为线索起点,优先处理 |
| 已有的 `decisions.yaml` | 必读,用于冲突检测和 ID 延续 |

### Step 2: 识别决策点

对材料做语义扫描,识别每一处"思想/逻辑/方案发生了变更"的地方。识别时:

1. 先看 `staged-signals.yaml` 里的积压标记,逐条尝试在原始材料中找到完整上下文,补全四要素
2. 再对材料做一次独立的全文扫描,补充自动感知阶段漏掉的变更点(自动感知不是完美的,漏检很正常)
3. 用 `references/signal-taxonomy.md` 中的"实质性变更"判断标准过滤掉纯措辞调整

### Step 3: 提取四要素

对每个决策点,提取:

| 要素 | 说明 |
|---|---|
| **触发因素** | 是什么引发了这次讨论/重新考虑?(用户提出的新约束、发现的问题、外部反馈、其他决策的连锁影响等) |
| **变更理由** | 为什么选择新方案而不是维持旧方案?决策依据是什么? |
| **关联项目元素** | 这个决策影响到哪些文件/模块/概念/其他决策?尽量给出可定位的引用(文件名、决策 ID) |
| **计划后续措施** | 当时说好了接下来要做什么?(如"下次要补充测试"、"待验证性能"、"需要同步给X模块") |

**信息不全时的处理原则:同自动感知阶段——不编造。** 某个要素在材料中确实找不到依据,就填 `null` 并标注 `待补全: true`,梳理完成后统一列出待补全项,请用户当场补充或留待下次。不要因为字段"看起来应该有值"就替用户编造。

### Step 4: 关联与冲突检测

对每条新提取的决策,检查它的 `related_elements` 是否与 `decisions.yaml` 中已有决策的 `related_elements` 重叠:

- 若重叠且新旧决策的结论**不矛盾**(新决策是旧决策的自然延伸)→ 记录 `supersedes` 关系
- 若重叠且结论**矛盾**,且没有任何一条决策显式说明"这取代了之前的XX方案"→ 标记为 ⚠️ **潜在冲突**,冲突检测规则见 `references/conflict-detection.md`

冲突不代表梳理出错,而是本 skill 真正的价值所在——把它们列出来交给用户判断,不要试图自己"和稀泥"替用户选边。

### Step 5: 写入与渲染

1. 将新决策写入 `decisions.yaml`(追加,不覆盖已有记录),ID 规则见 `references/record-schema.md`
2. 已被处理的 `staged-signals.yaml` 条目移除(标记为已纳入正式记录)
3. 按 `decisions.yaml` 全量重新渲染 `DECISION_LOG.md`(时间线形式,人类可读),渲染格式见 `references/record-schema.md` 末尾示例

### Step 6: 汇报摘要

向用户汇报,不要直接甩一整个文件让用户自己看,给出结构化摘要:

```markdown
## 📋 本次梳理结果

- 新增决策记录:N 条
- 处理积压标记:M 条(来自 staged-signals)
- 待补全项:K 条 —— [逐条列出决策ID + 缺失的要素]
- ⚠️ 潜在冲突:J 处 —— [逐条列出冲突的两条决策ID + 冲突点简述]

完整记录见 `.petrolpost/agent-decisions/DECISION_LOG.md`
```

若存在待补全项或冲突,主动询问用户是否现在处理,而不是把这个决定也留给用户去想起来问。

## 注意事项

- **不打断是自动感知阶段的硬约束,不是全量梳理阶段的约束。** 全量梳理时为了补全信息主动询问用户是合理的,不要把"不打断"错误地带入全量梳理阶段导致该问的也不问。
- **决策记录只增不改。** 方案又变了不是去改旧记录,而是新增一条决策并标注 `supersedes` 指向旧记录——历史本身也是要保留的信息。
- **区分"决策"和"讨论"。** 只有真正落地(哪怕是阶段性落地)的变更才算决策;还在权衡、没有结论的讨论不算,除非用户明确要求把"悬而未决的争议点"也单独记一类。
- **DECISION_LOG.md 是渲染产物,不是数据源。** 任何时候修正记录都改 `decisions.yaml` 再重新渲染,不要手工编辑 Markdown 文件导致两者不一致。
- **溯源。** 每条记录尽量保留 `source`(能定位回原始对话片段或文档位置),方便日后核实。
