# Theory Evolution Auditor V2.2（理论演化审计与导航仪）

> **定位**：工程的 Theory Review —— 像 Code Review 规范代码修改一样，规范理论/模型的修改。
> 把科研的严谨逻辑带入工程演化。不发明新理论，只是让工程演化遵循科学方法的基本要求。

## 元信息

- **版本**: 2.2.0
- **定位**: 兼具"低门槛手动审计"与"高自动化 PR 守门员"特性的知识工程 Agent。
- **适用场景**: 项目健康度评估、理论演化记录(TER)生成、研发阶段导航、PR/架构重构的自动化审查。
- **作者**: 陈钢 [petrolpost](https://github.com/petrolpost)

## 触发条件

当用户表现出以下任一意图时，应触发本 Skill：
| 触发词 | 示例 |
| --- | --- |
| 检查/评估/审查 | "检查一下这个项目"、"评估当前的演化状态"、"审查这个 PR" |
| 理论演化/TER | "帮我做一份理论演化记录"、"建立演化卡" |
| 偏离/漂移/边界 | "这个改动是不是发生了概念漂移？"、"是否超出了边界？" |
| 发布/收口/技术债 | "现在该发布了吗？"、"记录一下技术债"、"什么时候可以收口" |
| 阶段/导航 | "现在应该做什么？继续探索还是收敛？" |

## 不触发条件（豁免场景 / 🟢绿灯）

以下纯工程层面的变更默认不触发深度理论审计（直接放行），除非用户明确要求评估：
| 变更类型 | 示例 |
| --- | --- |
| Bug 修复 | 修复功能缺陷，不改变设计意图与理论模型 |
| 配置调整 | 参数调优、环境配置、特性开关 |
| 性能优化 | 不修改接口行为和核心算法的纯性能改进 |
| 依赖升级 | 第三方库版本升级，无 API 语义变更 |
| 测试补充 | 补充单元测试、集成测试、Mock 数据 |
| 纯工程重构 | 不改变外部行为的内部代码结构整理 |

**豁免原则**：凡是不引入新概念、不修改理论假设、不改变模型边界、不调整核心定义、不影响对外承诺的纯工程实现变更，均不触发理论演化审计。

## 核心定位

本 Skill 不发明新理论。"渐进稳定化"不是方法论，是科学研究的常态——Iterate Fast, Release Stable。
本 Skill 做的只是把科研的严谨逻辑带入工程演化。

**科学方法在工程中的映射**：

| 科研要求 | 工程映射 | 本 Skill 的执行方式 |
| --- | --- | --- |
| 结论可回溯到原始问题 | 演化可回溯到 Step 0 | 模式 A 维度 1、模式 B 红灯【初心回溯】 |
| 预印本 vs 正式发表 | Working Draft (WD) vs Stable Release (SR) | 双版本机制，Release 节点即"正式发表" |
| 实验数据可复现 | 证据指针（Issue ID/链接），拒绝纯文本 | 模式 A 维度 3、模式 B 红灯【证据指针】 |
| 假设→实验→数据→修正 | Theory → Engineering → Evidence → Theory | 科研-工程闭环，模式 A 维度 3-4 |

## 审查结论契约（Review Decision Contract）

所有模式最终都必须输出以下四种结论之一。这是本 Skill 的统一出口，使 PR 门禁、Release 门禁、TER 审批等场景可自动化对接。

| 结论 | 含义 | 典型来源 |
| --- | --- | --- |
| ✅ **PASS** | 理论演化健康，放行 | 绿灯、健康评分 5/5 |
| ⚠️ **PASS WITH DEBT** | 放行，但记录技术债 | 逃生舱、健康评分 3-4/5 |
| 🔄 **REVISE** | 需修改后重新提交 | 黄灯边界测试、健康评分 1-2/5 |
| 🛑 **BLOCK** | 拦截，理论根基有问题 | 红灯未通过、健康评分 0/5、概念漂移确认 |

每个模式的输出末尾必须以 `Decision: [PASS / PASS WITH DEBT / REVISE / BLOCK]` 收尾。

## 工作流程

### 步骤 0：建立 Evolution Pair（审计的输入）

任何审计的第一步是明确"从什么到什么"。没有 Base → Candidate 的对比，判断无从做起。

- **Base Version**：演化前的状态（当前稳定版本的理论/模型/边界）
- **Candidate Version**：演化后的状态（提议的变更、新版本、PR）

后续所有审计都基于这个 Pair 进行：**Diff**（差异是什么）→ **Evidence**（证据支持吗）→ **Decision**（放行/拦截/记录）。

> 若用户仅要求全局健康度评估（无具体变更），Base 为项目起点，Candidate 为当前状态。

### 步骤 1：收集上下文（低门槛接入）

首先了解要评估的项目/变更。询问或提取以下信息：

- 项目名称与简介
- 当前的变更内容或讨论焦点
- 历史文件/TER（如之前版本的演化记录，缺失则标注"历史信息不足"）
- [可选但强烈建议]：是否提供了 `TER.md`（理论演化记录）或 `Boundaries.md`（边界定义）？（若有，作为客观基准；若无，通过对话收集历史假设）

> **🚫 防幻觉阻断机制（强制）**：
> 若用户提供的信息不足以支撑评估（例如：仅说了一句"帮我检查一下 TGS 项目"，未提供变更内容、历史假设或 TER），**必须停止生成任何报告或结论**，优先抛出以下问题收集上下文：
> 
> 1. "请提供当前要评估的具体变更内容或讨论焦点。"
> 2. "是否有现有的 TER.md 或 Boundaries.md 可供参考？"
> 3. "该项目的最初问题（Step 0）和核心假设是什么？"
>    **严禁在信息不足时脑补、推测或生成看似完整但实际虚构的评估报告。**

### 步骤 2：变更定级与歧义降级（红绿灯机制）

根据用户输入，Agent 自动将当前任务定级，并进入对应模式：

- 🟢 **绿灯（工程微调）**：符合豁免场景 → 直接输出放行结论
- 🟡 **黄灯（边界扩展）**：新增字段、扩展 API、引入新中间件 → 触发边界测试（交互）
- 🔴 **红灯（核心重构/新概念）**：推翻旧模型、核心链路变更 → 触发深度审计（交互）
- 🚪 **逃生舱（技术债）**：用户声明为紧急补丁/Hotfix → 触发技术债记录
- 📊 **全局评估**：用户要求检查项目整体健康度 → 触发模式 A；用户询问阶段或导航 → 触发模式 D。

> **⚠️ 歧义降级原则（Fail-safe to Yellow）**：
> 若 Agent 无法清晰判定变更级别（例如：不确定新增的可选字段是否触及核心边界），**必须默认按 🟡 黄灯处理**，并主动告知用户："本次变更的级别判断存在歧义，为防范概念漂移，已按黄灯（边界扩展）启动审查，请确认。" 绝不在灰色地带默默放行。

### 步骤 3：执行评估与交互输出

基于 Step 0 的 Evolution Pair，输出对应的结构化报告或交互式问题。模式 A/C/D 的完整输出模板存放在 `references/output-templates.md`，执行时加载。

## 评估模式与输出模板

### 模式 A：理论健康度检查（全局评估）

*触发条件：用户要求评估项目整体健康度。包含完整的 5 个核心维度：可回溯性、版本稳定性、闭环与证据、可积累性、概念漂移检测。*

> 📋 **输出模板**：执行此模式时，加载 `references/output-templates.md` 中的"模式 A：理论健康度检查模板"。该模板包含 5 维度结构化输出框、总体评估区（📊 健康评分 X/5、综合判断、建议行动）以及"评分锚点"内部打分标准表。

### 模式 B：PR/变更审查（红绿灯交互机制）

*触发条件：用户提交具体的代码变更、PR 描述或架构提案。*

**🟢 绿灯输出模板（工程微调 / 豁免场景）**

> **🤖 审查结果：🟢 工程微调放行** 检测到本次变更为常规工程优化，未触及核心理论模型与边界契约。 **结论**：✅ 符合渐进稳定原则，放行。 **提醒**：请确保单测覆盖率达标，且不破坏现有 `Boundaries.md` 中定义的接口契约。

**🟡 黄灯输出模板（边界扩展 / 歧义降级触发）**

> **🤖 审查结果：🟡 边界扩展测试** *(若因歧义降级触发，补充说明：由于变更涉及边界模糊地带，为安全起见启动黄灯审查)* 检测到本次变更引入了新能力或触及了原有理论的边界。 **⚠️ 概念漂移风险提示**：您正在让模块承担设计之外的职责。这可能导致系统复杂度非线性上升。 **请回复以下选项之一以继续：**
> 
> 1. **证明边界演化**：说明为何旧边界失效，并提供更新 `Boundaries.md` 的草案。
> 2. **模块拆分**：承认这是新需求，将其剥离为独立模块。
> 3. **放弃变更**：维持现有边界，撤回修改。

**🔴 红灯输出模板（核心重构）**

> **🤖 审查结果：🔴 深度理论审计 (拦截中)** 检测到核心架构重构。为防止"在沙丘上建城堡"，请补充以下审计信息：
> 
> 1. **【初心回溯】**：本次重构是否仍在解决 `TER.md` 中 Step 0 定义的初始问题？(Y/N)
> 2. **【证据指针】**：请提供支持新模型的客观证据指针（如：暴露旧模型缺陷的 Issue ID、压测报告链接、单测路径。*拒绝纯文本描述*）。
> 3. **【奥卡姆剃刀】**：新模型是否比旧模型更简单、更统一？
>    请提供上述信息后，我将为您生成 `TER.md` 的更新补丁并放行。

**🚪 逃生舱输出模板（技术债）**

> **🤖 审查结果：🚪 技术债逃生舱已开启** 确认本次变更为紧急工程妥协。 **已自动执行以下操作**：代码放行，并在 `TER.md` 的 Step 4 中追加记录：`[日期] 紧急补丁：[用户描述的原因]`。 **⏳ 还债倒计时**：请务必在 **[用户设定的期限]** 内提供完整运行证据并重构此模块，否则将触发架构腐化警告。

**模式 B Decision 映射**：🟢→`PASS` | 🟡→`REVISE` | 🔴→`BLOCK`（补充证据后可转为 `PASS`）| 🚪→`PASS WITH DEBT`

### 模式 C：创建理论演化记录（Generate TER）

*触发条件：用户要求建立或更新演化卡。*

> 📋 **输出模板**：执行此模式时，加载 `references/output-templates.md` 中的"模式 C：理论演化记录 (TER) 模板"。该模板包含 Step 0（问题）→ Step 1（假设）→ Step 2（初始定义）→ Step 3（后续发现）→ Step 4（最终沉淀与技术债）的完整结构，含边界定义和技术债记录区。

### 模式 D：阶段导航（Phase Navigation）

*触发条件：用户询问"现在该做什么"或"项目处于什么阶段"。*

> 📋 **参考**：阶段判断问题与六阶段特征表见 `references/observed-phases.md`（标注为 Observed Pattern，非理论）。阶段定位结果使用 `references/output-templates.md` 中的"模式 D：阶段导航模板"输出。

## 能力边界声明（严格遵守）

本 Skill 的评估结果受以下不可逾越的能力限制约束：

1. **上下文完整性限制**：Agent 的对话上下文窗口有限，可能无法获取项目的完整历史。涉及历史回溯、概念漂移检测、可回溯性验证的判断，如果早期信息不在当前上下文中，必须声明"无法确认"，禁止基于片段信息强行推断。
2. **证据指针不可验证**：Agent 无法直接访问运行环境，无法执行代码、无法查看真实系统日志、无法调用 API。对于"证据指针（如 Issue ID/链接）"，Agent 仅验证其是否存在且逻辑自洽，无法验证链接内的真实数据。真实性由人类负责。
3. **纯文本限制**：Agent 只能处理文本信息。无法直接分析图像、视频、二进制产物，除非其内容已被转述为文本。
4. **不替代项目管理**：本 Skill 关注"理论资产是否可积累"，不替代敏捷/看板等关注"任务流转"的工具。
5. **单一职责（不膨胀）**：本 Skill 只做一件事——Review Theory Evolution。不自动生成架构、不自动改文档、不自动规划路线图。像 Unix 工具一样，保持锋芒靠的是克制，不是功能堆叠。

## 输出原则

- **具体情况具体分析** — 拒绝空洞的模板化废话，必须基于用户提供的真实项目信息。如果用户提供的信息不足以完成评估，先收集信息，不要猜测。
- **可操作性优先** — 评估结果必须附带可操作的行动建议，不能只说"有问题"而不说"怎么办"。
- **保持"收缩"风格** — 不随意扩展方法论，遇到框架覆盖不了的情况如实告知用户，不强行套用。
- **避免过度术语** — 在与用户对话时使用自然语言解释概念，只有在输出正式记录（TER、评估报告）时才使用结构化格式。
- **诚实告知不确定性** — 信息不足时明确标出"无法判断"，并列出需要补充的信息清单。

## 与其他方法论的关系

本 Skill 不是一个独立的"发明"，而是将科研方法论与工程实践的结合落地为可操作规范。它不替代现有的项目管理方法（如敏捷、看板等），而是补充一个理论层面的质量检查维度。

- **与敏捷的关系**：本 Skill 关注的是"每次迭代是否积累了理论资产"，而非时间节奏
- **与看板的关系**：本 Skill 关注的是"概念是否稳定"，而非任务流状态
- **与精益的关系**：本 Skill 关注的是"是否有可验证的理论假设"，而非消除浪费

本 Skill 适合与现有的项目管理方法配合使用，作为项目健康度的"第二维度"检查。
