# Theory Evolution Auditor

Engineering's "Theory Review" — 像 Code Review 规范代码修改一样，规范理论/模型的修改。把科研的严谨逻辑带入工程演化，确保每次迭代都是可积累的。

## 定位

本 Skill 不发明新理论。"渐进稳定化"不是方法论，是科学研究的常态——Iterate Fast, Release Stable。本 Skill 做的只是把科研的严谨逻辑带入工程演化。

**科学方法在工程中的映射**：

| 科研要求 | 工程映射 | 执行方式 |
|---------|---------|---------|
| 结论可回溯到原始问题 | 演化可回溯到 Step 0 | 模式 A 维度 1、模式 B 红灯【初心回溯】 |
| 预印本 vs 正式发表 | Working Draft (WD) vs Stable Release (SR) | 双版本机制，Release 节点即"正式发表" |
| 实验数据可复现 | 证据指针（Issue ID/链接），拒绝纯文本 | 模式 A 维度 3、模式 B 红灯【证据指针】 |
| 假设→实验→数据→修正 | Theory → Engineering → Evidence → Theory | 科研-工程闭环，模式 A 维度 3-4 |

## 核心流程

所有审计基于 **Evolution Pair**（Base→Candidate）进行：

```
Step 0: 建立 Evolution Pair
         │
         ▼
Step 1: 收集上下文（项目、变更、TER/Boundaries）
         │
         ▼
Step 2: 变更定级（红绿灯机制）
         │
         ▼
Step 3: 执行评估与输出 Decision
```

### 审查结论契约（统一出口）

所有模式最终都输出以下四种结论之一：

| 结论 | 含义 | 典型来源 |
|------|------|---------|
| ✅ **PASS** | 理论演化健康，放行 | 绿灯、健康评分 5/5 |
| ⚠️ **PASS WITH DEBT** | 放行，但记录技术债 | 逃生舱、健康评分 3-4/5 |
| 🔄 **REVISE** | 需修改后重新提交 | 黄灯边界测试、健康评分 1-2/5 |
| 🛑 **BLOCK** | 拦截，理论根基有问题 | 红灯未通过、健康评分 0/5、概念漂移确认 |

## 工作模式

### 模式 A：理论健康度检查（全局评估）

评估项目整体健康度，包含 5 个核心维度：

1. **可回溯性** — 是否仍能回答最初的问题
2. **版本稳定性** — 是否有明确的稳定版本
3. **闭环与证据** — 理论→工程→证据的闭环是否完整
4. **可积累性** — 是否有 Release 节点和假设验证记录
5. **概念漂移检测** — 核心假设是否仍然有效

### 模式 B：PR/变更审查（红绿灯机制）

| 等级 | 含义 | 输出 |
|------|------|------|
| 🟢 绿灯 | 工程微调，符合豁免场景 | 直接放行 |
| 🟡 黄灯 | 边界扩展，触及理论边界 | 交互测试，需用户确认 |
| 🔴 红灯 | 核心重构，推翻旧模型 | 深度审计，需补充证据 |
| 🚪 逃生舱 | 技术债，紧急补丁 | 放行但记录技术债 |

**Decision 映射**：🟢→PASS | 🟡→REVISE | 🔴→BLOCK | 🚪→PASS WITH DEBT

### 模式 C：创建理论演化记录（Generate TER）

生成结构化的理论演化记录，包含：

- Step 0：问题（Problem）
- Step 1：假设（Hypothesis）
- Step 2：初始定义（Version 0.x）
- Step 3：后续发现
- Step 4：最终沉淀与技术债

### 模式 D：阶段导航（Phase Navigation）

判断项目当前阶段，提供导航建议。阶段特征参考见 `references/observed-phases.md`（标注为 Observed Pattern，非理论）。

## 触发条件

当用户说以下内容时触发：

| 触发词 | 示例 |
|--------|------|
| 检查/评估/审查 | "检查一下这个项目"、"评估演化状态"、"审查这个 PR" |
| 理论演化/TER | "帮我做一份理论演化记录"、"建立演化卡" |
| 偏离/漂移/边界 | "是不是发生了概念漂移？"、"是否超出了边界？" |
| 发布/收口/技术债 | "现在该发布了吗？"、"什么时候可以收口" |
| 阶段/导航 | "现在应该做什么？继续探索还是收敛？" |

## 不触发条件（豁免场景）

以下纯工程变更默认不触发深度审计：

- Bug 修复（不改变设计意图）
- 配置调整（参数调优、环境配置）
- 性能优化（不修改接口行为和核心算法）
- 依赖升级（无 API 语义变更）
- 测试补充（补充单元测试、集成测试）
- 纯工程重构（不改变外部行为）

## 能力边界

1. **上下文完整性限制**：对话上下文窗口有限，早期信息不在上下文中时声明"无法确认"
2. **证据指针不可验证**：仅验证证据指针的存在和逻辑自洽，真实性由人类负责
3. **纯文本限制**：只能处理文本信息
4. **不替代项目管理**：关注理论资产是否可积累，不替代敏捷/看板等工具
5. **单一职责**：只做 Theory Review，不自动生成架构、改文档、规划路线图

## 输出原则

- **具体情况具体分析** — 拒绝空洞的模板化废话
- **可操作性优先** — 评估结果必须附带行动建议
- **保持"收缩"风格** — 不随意扩展方法论
- **避免过度术语** — 对话使用自然语言，正式记录使用结构化格式
- **诚实告知不确定性** — 信息不足时明确标出"无法判断"
